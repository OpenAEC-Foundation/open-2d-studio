Architectuur-benaderingen: Parametric Constraint Engine

Kies de aanpak die het beste past bij Open 2D Studio

A

Constraint Graph Engine (Aanbevolen)

Een Directed Acyclic Graph (DAG) als kern. Elke parameter is een node, elke formule/constraint is een edge. Topologische sort bepaalt de solve-volgorde. Circulaire afhankelijkheden worden geblokkeerd bij invoer.

Voordelen

  • Bewezen patroon (FreeCAD, SolveSpace, Fusion 360)
  • Incrementeel updaten: alleen downstream nodes herberekenen
  • Dependency graph direct bruikbaar als debug/visualisatie tool
  • Cross-object referenties (@Object.param) passen er natuurlijk in
  • Past bij bestaande ParameterDefinition.dependencies veld

Nadelen

  • Graph-datastructuur toevoegen aan state
  • Formule-parser nodig (expressie-evaluator)
B

Spreadsheet Model

Parameters als cellen in een spreadsheet. Formules verwijzen naar andere cellen via adressen. Reactive herberekening bij wijziging. Vergelijkbaar met hoe Excel werkt.

Voordelen

  • Zeer intuïtief voor gebruikers (iedereen kent Excel)
  • Formule-syntax is bekend (=A1*2)
  • Flat data model, makkelijk te serialiseren

Nadelen

  • Minder geschikt voor geometrische constraints op edges/vertices
  • Cross-object referenties worden omslachtig (SheetName!Cell)
  • Mismatch met bestaande type-gebaseerde architectuur
  • Moeilijker te visualiseren als dependency graph
C

Entity-Component Constraints

ECS-achtig: shapes zijn entities, parameters en constraints zijn components. Een constraint solver system loopt over alle constraint-components en resolved ze. Zeer modulair.

Voordelen

  • Zeer modulair en uitbreidbaar
  • Makkelijk nieuwe constraint-types toevoegen
  • Past goed bij een plugin-architectuur

Nadelen

  • Grote architectuurwijziging nodig (huidige code is niet ECS)
  • Overhead voor een 2D CAD applicatie
  • Complexer dan nodig voor fase 1
  • Lastige migratie van bestaande ParametricShape types
